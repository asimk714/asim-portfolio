Experiment Tracker is a local-first Flask + SQLite experiment log that closes the loop between running an experiment and recording what you concluded from it — including the decision and the next action. It is intentionally small. The evidence is about what was prioritized and why, how it was verified, and what it deliberately does not claim.

Context

I run experiments. Small ones. Local ones. Things like "does this approach work better than that one" or "what happens if I change this variable." I was losing the conclusions.

The problem wasn't running experiments. It was that the experiments, the runs, and the conclusions lived in different places — a notes file here, a results folder there, a memory of what I decided somewhere else. The loop between "I tested something" and "I know what to do next" was broken.

What this is

A local-first Flask + SQLite experiment log. Create experiments. Add runs. Compare runs. Most importantly: record a conclusion for each experiment — the outcome, the decision, and the next action — and connect it back to the experiment it came from.

What this is not

It is not a cloud product. It is not multi-user. It has no authentication. It has no charts or visualization. It is not a collaboration tool. It is a personal local tool for a specific job: keeping experiments and their conclusions connected.

Problem

Surface problem: experiments and their conclusions were disconnected. I'd run something, decide something, and later lose the thread.

Deeper problem: the gap between experimentation and decision was unstructured. Without a place to record what you concluded and what you'd do next, the experiment doesn't change what you do — it just sits there as a memory.

Core question

How do you store what you tested, record what you concluded, and connect it to what you do next — without overcomplicating the tool?

Why It Mattered

The value of an experiment is not the run. It's the decision that follows from it. A tool that lets you record runs but not conclusions is a partial solution — it captures the activity but not the value.

Making the conclusion first-class — with outcome, decision, next action, and timestamps — is what turns an experiment log into something that actually changes what you do next. That's the product judgment: the smallest thing that closes the loop.

Users / Assumptions

Target user (inferred): someone who runs small experiments locally and wants to keep them connected to decisions — a practitioner, a builder, someone who tests things and wants to remember what they learned.

Assumption: a single-user local tool is sufficient for this job. Multi-user, auth, cloud — all of those would add complexity without adding value for the intended user.

Hypothesis

Single-user local-first is the right scope for this tool. Not validated with external users — inferred from the intended use case.

Not evidenced

No external user research. No external users. No measured adoption. No launch.

Product Framing

The product principle, stated once and used everywhere: Store what you tested. Record what you concluded. Connect it to what you do next.

The product question, stated narrowly: what is the smallest capability that closes the loop between experiment and decision? Not "what's the most impressive experiment tool?" — "what's the smallest thing that actually closes the loop?"

The principle is the throughline

Conclusion capture is the core. Everything else in the brief is evaluated against whether it closes the loop faster or slower. The prioritization trade-offs all come from this question.

Prioritization

Seven candidates were evaluated. One was chosen.

# Candidate Decision Why
1 Conclusion capture Chosen Closes the loop. Smallest capability that does the job.
2 Charts / visualization Not prioritized Nice-to-have. Doesn't close the loop faster.
3 Search / filter improvements Not prioritized Scale problem. Not needed at local scale.
4 Authentication / multi-user Not prioritized Overkill for a local personal tool.
5 Cloud database Not prioritized Adds deployment complexity. Local-first is the point.
6 AI features Not prioritized Distraction. The job is recording, not generating.
7 Experiment templates Not prioritized Nice-to-have. Not in the smallest loop.
8 Artifact linking / file uploads Not prioritized Out of scope for v1.

The prioritization is the most important part of this case study. It shows the product thinking: what was chosen, what was deliberately not chosen, and why. The "why not prioritized" column is as important as the "chosen" column.

Solution

The solution is a Flask + SQLite + Jinja2 web app. No JavaScript framework. No CSS framework. Vanilla. The pages: dashboard, create/edit experiment, experiment detail, create/edit run, run detail, compare runs, dashboard, conclusion form.

  1. Experiments — create, edit, delete. Title, description, tags, status.
  2. Runs — create, edit, delete. Name, hypothesis, result, notes, timestamps.
  3. Conclusion — the core. Outcome, decision, next action, plus timestamps. One conclusion per experiment. Created when you record it; updated when you change it.
  4. Compare — select two runs, see them side by side.

The conclusion model is the product

Four fields: outcome, decision, next_action, plus decided_at, created_at, updated_at. That's it. The smallest thing that closes the loop. One-conclusion-per-experiment constraint keeps it clean. Cascade delete keeps it consistent.

Architecture / Implementation

Stack: Python 3, Flask, SQLite, Jinja2. No JS framework. No CSS framework. Dependencies: gunicorn (production server). Minimal.

Database: SQLite. Schema has experiments, runs, conclusions, and a conclusions_updated_at trigger. One-conclusion-per-experiment enforced by UNIQUE(experiment_id) on the conclusions table. Cascade: experiment deleted → runs + conclusion deleted.

Conclusion capture implementation: schema (~3 lines added), db.py (create_or_update_conclusion, get_conclusion — ~23 lines), templates (conclusion form, run detail, experiment detail — ~27 lines across 3 files). Small, verifiable, real.

Verified by test

Database integrity verified: FK CASCADE, UNIQUE constraints, triggers all work. One-conclusion-per-experiment enforced. Cascade deletion works. Run detail route wired. Compare workflow works. Error handling for nonexistent experiments/runs works.

Missing

Browser rendering not verified — Termux environment has no GUI browser. Flask test client verifies HTML generation (10 HTML tests included in the 22), but it is not a browser.

Metrics

The product deliberately does not claim any measured outcomes. The only proposed metric is a usage metric — a way to know whether the conclusion feature is actually being used.

Proposed

experiments_with_conclusion / completed_experiments — the proportion of completed experiments that have a recorded conclusion. A measure of whether the core feature is actually being used. Proposed. Not measured.

Not evidenced

No measured product outcomes. No usage data. No adoption metric. The product is local-first and personal; there is no telemetry by design.

Learnings

1. The smallest thing that closes the loop is the product. Conclusion capture is four fields. That's the whole product insight. Everything else is scope management — and the prioritization of what to leave out is the real product judgment.

2. Verification is not self-assessment. The 17-category report is an independent post-implementation review. Testing the database, the constraints, the routes, the HTML generation — that's different from claiming the product is "done" because it runs. It's a real verification.

3. Don't claim what you haven't measured. The proposed usage metric exists as a proposal. The product does not claim adoption, outcomes, or users it doesn't have. That's the discipline.

4. Code review is not browser testing. Accessibility and security were verified by code review. That's real verification with a real limitation — and the limitation is stated plainly rather than hidden.

What I Would Do Next

  1. Validate the user model with real people who run experiments locally. Is single-user local-first the right scope?
  2. Measure the usage metric if the product were in use: experiments_with_ conclusion / completed_experiments. Is the conclusion feature actually being used?
  3. Add search/filter — the first v2 candidate, because at some scale you need to find experiments.
  4. Add artifact upload — link files to experiments, so the evidence lives with the conclusion.
  5. Add visualization — charts of experiment outcomes over time. Nice-to-have, not core.
Proposed

None of the above has been done. They are next steps, not evidence.
