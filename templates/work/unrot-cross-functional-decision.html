What This Artifact Is

This is a portfolio exercise. It demonstrates a cross-functional product decision process — how I would structure a conversation across business, product, UX, data, engineering, and QA/operations around a single meaningful trade-off.

The scenario is set inside the Unrot Daily Retention product context because that is where the strongest existing portfolio evidence lives: a documented measurement model, an A/B experiment plan with power analysis, a real Next.js 16 + PostgreSQL + Prisma application, and documented problem framing plus JTBD/intervention hypotheses. Those artifacts are real and verified. The decision exercise itself is simulated.

The Problem That Drives the Decision

Unrot's surface problem is low D1 retention — people visit, then don't return the next day. The deeper hypothesis in the Unrot case study is that the problem may be the handoff between sessions: the user completes the first lesson but has no reason to return tomorrow. The product may be excellent at first-session value and poor at tomorrow's reason-to-return.

The measurement model defines D1 and instruments the funnel; the A/B plan is written; the analytics dashboard computes from real events but currently shows "not enough real cohort data yet." The JTBD and intervention hypotheses (H1–H7) are documented but not validated with real users.

A business stakeholder — in this simulated scenario, someone accountable for whether Unrot creates a retention outcome — is pressing for a visible next step. The question is not "do nothing." It is: which intervention, if any, do we test now, and what are we accepting by choosing it?

This is a prioritization-and-measurement-confidence decision, not a build-vs-not-build decision. Both sides agree the team should test something. The disagreement is about when to test and whether the user model behind the test is reliable enough to make the test worth the opportunity cost of not testing something else.

Business / Stakeholder Accountable for whether Unrot creates a retention outcome

Question

Are we moving the right metric, and are we moving it for the right reason — or are we optimizing a first-session number that doesn't actually cause return?

Concern

Time-to-evidence pressure: the team has a measurement system and an A/B plan but no real cohort data yet. A stakeholder accountable for retention wants to see whether the product can move D1 at all, and wants that evidence sooner rather than later. The concern is the cost of waiting for perfect user-model validation when the cost of a bad test is a wasted experiment slot and a misleading signal.

Decision input

Provided: "I need to know whether we can move D1. I'd rather test something real and learn than wait indefinitely. But I also need the test to be interpretable — if it wins, I need to be able to say it moved D1 for the right reason, not just that a number went up." Simulated

Product (PM) Translate the problem into a decision

Problem framing

The deepest documented Unrot hypothesis is that the problem is the handoff between sessions, not the first session alone. Any intervention chosen should target return behavior, not just first-session completion. The PM's job is to make sure the decision respects that framing rather than defaulting to the easiest first-session improvement.

Scope

For this decision, scope is one intervention for one A/B test. Not a multi-intervention program, not a redesign. One hypothesis, one test, one primary metric (D1).

Priority

Prioritize the intervention with the highest probability of targeting the deeper problem and the lowest risk of producing an uninterpretable result. If two interventions are close, prefer the one whose failure would still teach us something about the user model.

Trade-offs

Testing H4 now means accepting that the JTBD/intervention hypotheses are unvalidated. Testing nothing until validation means accepting delay and the risk that the user model is wrong in a way we won't discover until we test. The PM must choose which uncertainty to carry.

Success criteria

A successful decision here is not "the test wins." It is: the team runs a test that is interpretable, learns something about the user model whether it wins or loses, and does not spend the opportunity cost of a misleading test. The measurement status of the outcome is defined before the decision is made.

UX / Design User flow, usability risk, interaction implications

User flow

H4 (return-intent nudge at lesson completion) is a post-action interaction: after the user completes a lesson, the product asks whether they intend to return tomorrow, and if yes, offers a concrete commitment (for example, a reminder or a "tomorrow's mission" preview). This is a flow that sits between sessions — exactly the handoff the deeper hypothesis identifies.

Usability risk

Low (proposed assessment, simulated): a single post-completion prompt is low-risk in isolation. The bigger risk is change to the completion experience: if the nudge makes the completion moment feel like a request rather than a reward, it could depress lesson completion itself. That would confound the D1 signal — a drop in completion could mask a real D1 improvement, or a D1 improvement could be driven by a completion drop that we don't notice.

Interaction implications

The nudge needs a concrete commitment outcome (reminder, preview, or similar) to be more than a survey question. Without a commitment mechanism, the return-intent prompt is a measurement instrument, not an intervention — and testing it as an intervention would be a weak test.

UX validation

Proposed — not yet done (simulated) No UX research has validated the return-intent prompt wording, the commitment mechanism, or the risk that the prompt depresses completion. Proposed UX validation before the test: a small unmoderated task + comprehension check on the prompt + commitment flow, with a clear "this is a portfolio exercise, not validated research" label.

Data / Analytics Metric, measurement method, success threshold

Metric

Primary: D1 retention — fraction of users who start a lesson on day D and return to start another lesson on day D+1. This is the metric the Unrot measurement model defines and the A/B plan targets.

Supporting metrics

Lesson completion rate (guardrail), reminder opt-in rate (mechanism check), return-intent prompt response rate (instrument check), D1 among prompt-responders vs. prompt-skippers (segment check).

Measurement method

A/B test with randomized user-ID assignment, 50/50 allocation, deterministic hash assignment (as specified in the Unrot A/B plan). Primary analysis on D1. The analytics dashboard already computes from real events — the test would populate it with a real cohort for the first time.

Baseline requirement

Not yet measured (proposed). The A/B plan specifies ~650–700 users per variant and ~1,300–1,400 total, with 2-week duration + 2-day cooldown. The current analytics dashboard shows "not enough real cohort data yet" — there is no closed cohort to establish a baseline D1 from. The first real test would also be the first real baseline.

Success threshold

Defined in the A/B plan as part of the decision rules (win / inconclusive / loss). Not reproduced here — the threshold is an existing Unrot artifact. The data function's input to the decision is that any test needs a closed cohort and enough power to be interpretable, and that a test run before a baseline exists is still interpretable if the analysis treats the first cohort as the baseline.

Engineering Feasibility, architecture, dependencies, technical risk

Feasibility

Feasible (proposed assessment, simulated). Unrot already has auth, sessions, lesson progress tracking, reminder preferences (UserPreference model), and analytics events. The return-intent nudge is a post-completion interaction that can reuse the existing session/lesson-completion boundary. The commitment mechanism (reminder or "tomorrow's mission" preview) can reuse the existing reminder preference and lesson-scheduling structure.

Architecture implications

One new event type (return_intent_responded) and one new prompt exposure event. One new UI surface at lesson completion. One new preference/commitment state. No new service, no new database, no new external dependency. The engineering surface is small relative to the measurement upside.

Dependencies

Completion event boundary must be well-defined so the prompt does not fire spuriously (e.g., on non-completion returns to the lesson page). Reminder delivery path must be validated before the test — if reminders don't actually fire, the commitment mechanism doesn't work, and the test is testing a broken intervention.

Implementation complexity

Low-to-medium (proposed assessment, simulated). Small surface, but the correctness of the completion-boundary and reminder-delivery assumptions matters more than the UI effort. The engineering risk is not "can we build it" but "are the assumptions the test relies on true."

Technical risk

The measurement depends on clean event instrumentation at the completion boundary. If the prompt fires at the wrong moment, or if reminder delivery is unreliable, the test's interpretability degrades. This is a measurement-confidence engineering risk, not a build risk.

QA / Operations Acceptance criteria, regression, rollout, monitoring

Acceptance criteria

See the Acceptance Criteria section below. In brief: the prompt fires only on genuine lesson completion, the commitment mechanism is wired, the event instrumentation is correct, the randomization is correct, and the dashboard shows the cohort state honestly.

Regression concerns

The prompt must not fire on non-completion page views. The reminder delivery path must not regress. The new events must not break existing analytics queries. The completion moment itself must not regress in latency or reliability.

Rollout considerations

A/B test with 50/50 allocation is the rollout mechanism. No gradual rollout needed for a single prompt — the risk surface is small. The bigger rollout question is: if the test wins, what is the generalizable intervention, not just the one prompt wording.

Monitoring requirements

During the test: prompt exposure rate, prompt response rate, reminder opt-in rate, reminder delivery confirmation, lesson completion rate (guardrail), D1. After the test: a clear decision record capturing the outcome, the decision, and the next action — exactly the loop the Experiment Tracker product was built to close.

The Decision, the Trade-off, and What Would Change It

Run the return-intent nudge (H4) as the first A/B test — but only after three pre-test verification items are confirmed, and only with the guardrails below.

The reasoning is not that H4 is the best intervention in absolute terms. It is that H4 has the highest combination of (a) direct alignment with the deeper documented hypothesis (the session handoff), (b) small engineering surface, and (c) high learning value even if it loses — provided the pre-test verification items are confirmed. The alternative (hold for validation first) carries its own risk: a hold that does not end in a real, acted-on validation is just delay, and the measurement system is already built to support a first test.

This is a proposed decision for the portfolio exercise. It is not an approved decision, not a decision that was made, and not a decision backed by real stakeholders. The artifact exists to show the structure of the reasoning, not to claim a real outcome.

What we prioritize

  • One intervention for one interpretable A/B test. H4, with a concrete commitment mechanism, run against D1 as the primary metric.
  • Pre-test verification before the test runs. The three items below must be confirmed before the test is launched — not after.
  • Measurement confidence over speed. The test runs because the engineering surface is small and the learning value is high, not because speed is the priority. The guardrails below are non-negotiable.

What we defer

  • Validating the full JTBD/intervention hypothesis set with real users. Deferred until after the test — not because it is unimportant, but because the test is the faster path to a real learning signal, and the test result will inform what validation to prioritize.
  • Testing a second intervention (e.g., H5 or H6) in the same window. Deferred. One test at a time, with a clean primary metric. A second intervention would dilute the interpretability of the first.
  • Generalizing the intervention beyond the specific prompt wording. Deferred until after the test shows a signal. The first test is about whether the mechanism moves D1, not about the perfect wording.
  • A multi-intervention program. Deferred. This is one decision, one test, one primary metric.

Why

The deeper Unrot hypothesis — that the problem is the handoff between sessions — is the right problem to target, and H4 is the intervention most directly aimed at that handoff among the documented options. The engineering surface is small and reuses existing structure. Most importantly, a losing H4 test still teaches us something about the user model (did the commitment mechanism move D1? did completion drop? did reminder delivery work?), whereas a hold that ends in nominal validation teaches us less.

The counter-argument — that testing before user validation risks a misleading result — is real and is addressed by the pre-test verification items and guardrails below. The decision accepts the measurement-confidence risk because it is bounded and because the alternative carries its own risk.

  • Pre-test verification fails. If the completion boundary cannot be instrumented cleanly, or if reminder delivery cannot be confirmed, the test's interpretability is compromised and the decision should be held until those are fixed.
  • A real user-validation study changes the hypothesis. If validation (when it happens) shows the handoff problem is not the dominant issue, H4 is no longer the best target and the decision should be reconsidered.
  • The stakeholder's underlying question changes. If the accountable stakeholder shifts from "can we move D1 at all" to "we need a specific D1 number by a specific date," the decision framework changes — and the PM should flag that the portfolio exercise does not include a real stakeholder with a real deadline.
  • A better-understood intervention emerges. If a different intervention has a clearer link to the deeper hypothesis and a similarly small surface, the comparison should be re-run.

Acceptance Criteria

These are the acceptance criteria for the intervention and the test setup, not for a business outcome. They define what must be true before and during the test. None of them is a claim that the test will win.

  1. AC-1 · Prompt fires only on genuine lesson completion

    Given a user completes a lesson, when the completion event fires, then the return-intent prompt is shown once and only once for that completion — and is not shown on non-completion page views, on lesson retries, or on navigation that does not constitute a completion.

  2. AC-2 · Commitment mechanism is wired

    Given a user responds to the return-intent prompt with a commitment, when the commitment is recorded, then a reminder or "tomorrow's mission" preview is scheduled against the existing reminder preference / lesson-scheduling structure — and the commitment is reflected in the user's state.

  3. AC-3 · Reminder delivery is confirmed before the test

    Given the reminder path is used as the commitment mechanism, when a reminder is scheduled, then the delivery path is verified to fire (in a pre-test verification step, not inferred from the test itself) — because a broken delivery path would make the test test a broken intervention.

  4. AC-4 · Event instrumentation is correct

    Given the test runs, when a user is exposed to the prompt, then a prompt_exposure event is emitted; when the user responds, then a return_intent_responded event is emitted with the response and commitment; and both events carry the standard properties (eventName, propertiesJson, occurredAt, sessionId, route, userId) required by the Unrot measurement model.

  5. AC-5 · Randomization is correct

    Given a user is eligible for the test, when the user reaches the lesson-completion boundary, then the user is assigned to control or variant by deterministic user-ID hash with 50/50 allocation, and the assignment is stable for the duration of the test.

  6. AC-6 · Completion rate is monitored as a guardrail

    Given the test runs, when lesson completion rate is tracked, then a material drop in completion in the variant relative to control is flagged — because a D1 improvement driven by a completion drop would be an uninterpretable result, not a real win.

  7. AC-7 · Dashboard shows the cohort state honestly

    Given the test runs, when the analytics dashboard renders, then it shows the cohort state honestly — including "not enough real cohort data yet" until a cohort has closed, and the test cohort when one exists. No D1 number is fabricated to fill an empty state.

  8. AC-8 · Decision is recorded after the test

    Given the test concludes, when the outcome is known, then a decision record is created capturing the outcome, the decision, and the next action — the same loop the Experiment Tracker product was built to close, applied here to the test itself.
