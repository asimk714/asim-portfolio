Unrot is a Next.js 16 + PostgreSQL + Prisma daily micro-learning retention prototype. It demonstrates how to frame a retention problem, design a measurement system before validating anything, and build a production-shaped analytics dashboard — while being honest that the D1 retention outcome was never measured.

View on GitHub Working prototype — local/demo environment · no verified public deployment Back to Proof of Work

Context

A daily micro-learning product sends users a short lesson each day. The behavioral target is D1 retention — does the user come back the next day?

The surface problem: D1 retention is low. The assignment gave a baseline of 16% and a target benchmark of 22% — both assignment-provided context, not author-measured. The deeper question is not "make the first session better." It's whether the handoff between sessions is where the retention actually breaks.

What this is

A real Next.js 16 + PostgreSQL + Prisma application. Auth, sessions, learning paths, lessons, lesson progress, reminder preferences, analytics events. The analytics dashboard computes from real events. The measurement model is real.

What this is not

It is not a live product with a real user base. It is not a retention solution that was validated with outcomes. The portfolio evidence is about measurement thinking and product rigor — not about a solved retention problem.

Problem

Surface problem: low D1 retention. People visit, then don't return the next day.

Deeper hypothesis: the problem may be the handoff between sessions — the user completes the first lesson but has no reason to return tomorrow. The product may be excellent at first-session value and poor at tomorrow's reason-to-return.

Core question

What creates a reason to return — not a reason to start?

This framing is the most important product thinking in the case. It separates first-session optimization from return-session optimization, and it's why the measurement model and the intervention hypotheses focus on return behavior, not just first-session completion.

Why It Mattered

Retention is the metric that separates a product people try from a product people keep using. Low D1 retention means the product is not yet creating enough reason to return — and fixing that is a product problem, not a marketing problem.

The measurement-model-first approach matters because most products measure retention after the fact, if at all. Designing the measurement before building anything is how you avoid building a product you can't tell is working.

Users / Assumptions

The product defines user segments via a UserPreference model: role (product-manager, software-engineer, general), goal (staying-current, interview-prep, upskilling), experience (beginner, intermediate, advanced).

These segments are defined in the schema. They have not been validated with real users. They are inferred from the product's intended audience, not from research.

Inferred

User segments are defined in the schema but not validated with real users. Reasonable inference; not evidence.

Hypothesis

JTBD hypotheses (4 jobs: interview prep, AI news, AI fundamentals, practical application) and 7 intervention hypotheses (H1–H7) are documented — in the problem-framing research. None validated.

Product Framing

The product question, stated narrowly: how do we give a daily micro-learning user a reason to return tomorrow? Not "how do we make the lesson better?" — how do we make the return feel worth it.

The product principle, stated once and used everywhere: measure the outcome you care about before you claim you've changed it.

The principle is the throughline

Everything downstream — the measurement model, the analytics dashboard showing "not enough real cohort data yet," the baseline/target shown as context labels, the experiment plan, the honest "no meaningful externally validated outcome" — is a consequence of this principle.

Discovery / Research

Seven candidate reasons for low D1 retention are organized by category: first-session value gap, no cue/trigger, no progress mechanic, friction, audience mismatch, and measurement issues.

Prioritization

The product prioritizes measurement before optimization. Before building any intervention, the product builds the measurement system: what events to instrument, what the funnel is, what D1 means, how cohorts are computed, what "not enough data" looks like.

Verified

Measurement-first: the analytics dashboard, the D1 retention calculator, the event schema, the funnel, the cohort completeness rule — all built before any intervention is validated. Real code exists.

Verified

A/B experiment plan: rigorous design with randomization unit (user ID), 50/50 allocation, deterministic hash assignment, primary/secondary/guardrail metrics, sample size power analysis (~650–700 per variant, ~1,300–1,400 total), 2-week duration + 2-day cooldown, decision rules. Real document.

Solution

  1. User authentication + sessions — signup, login, session management. Real routes, real form, real database models.
  2. Learning paths + lessons — a library of short daily lessons organized into paths. Real schema, real pages.
  3. Lesson progress tracking — which lessons a user has started/completed. Real progress model.
  4. Reminder preferences — timezone-aware reminder scheduling with a timezone auto-detection form. Real timezone picker, real schema.
  5. Analytics dashboard — KPI grid, 8-step funnel, daily cohort table, event taxonomy audit. Computes from real events. Shows "not enough real cohort data yet" honestly.
  6. D1 retention calculator — calendar-day logic in the user's IANA timezone, UTC fallback, excludes demo return previews, cohort completeness rule. Pure TypeScript, decoupled from database syntax.

The analytics dashboard is the flagship artifact

It computes from a real database. It shows baseline and target as context labels, not results. It shows an illustrative cohort model clearly labeled as a "benchmark model." It shows "not enough real cohort data yet" when there are no closed cohorts. This is what honest measurement design looks like in a product.

Architecture / Implementation

Stack: Next.js 16 App Router + TypeScript + Tailwind CSS + PostgreSQL + Prisma 7 ORM + Zod. Pnpm package manager. Production-shaped, not a toy.

Authorization: server-side auth via session cookies. Login, signup, auth actions. Server Components read the session; client-side components get the session via a hook. Prisma schema has a Session model with userId foreign key, createdAt, expiresAt, revokedAt. IP-based rate limiting on login/signup.

Database: PostgreSQL via the driver adapter pattern (separate connection for HTTP server vs. server actions). Connection pooling (max: 10, SSL in production). Serverless compatibility design — Vercel + Neon deployment target.

Analytics: AnalyticsEvent model with eventName, propertiesJson (JSON), occurredAt, sessionId, route, userId. Events are recorded from the app and queried by the analytics dashboard. The D1 retention calculator is decoupled from database syntax — pure TypeScript that works on any list of events.

Verified

Architecture document exists. Prisma schema (7 models) exists. Auth system exists. Health endpoint exists (/api/health). Build, lint, typecheck pass. ESLint 0 errors / 0 warnings.

Not evidenced

No live deployment with real users. No production traffic. The deployment design (Vercel + Neon) is documented; the actual deployment with a real audience is not evidenced.

Learnings

1. Measure before you optimize. The strongest thing this product did was build the measurement system before building any intervention. You can't tell if a retention intervention worked if you didn't define what "worked" means and how to measure it.

2. The handoff between sessions is a different product problem from the first session. First-session value and next-day return are related but not the same thing. Treating them as the same problem produces products that are good at one and bad at the other.

3. Honest "not enough data" is better than invented data. The analytics dashboard shows a real state — no closed cohorts means no D1 returners to report. That's the truth. Fabricating a number would be the opposite of the product discipline this case is trying to show.

4. A rigorous experiment plan is itself evidence of product thinking. The A/B plan with power analysis, decision rules, guardrails, and sample size calculation is a real artifact. It shows how I'd run the experiment if I had users. That's not the same as having run it.

What I Would Do Next

  1. Validate the JTBD hypotheses with real users — the 4 jobs, the 7 intervention hypotheses, and especially the lead intervention ("Tomorrow's 5-Minute Mission" package).
  2. Run the A/B experiment the way the plan describes — real randomization, real allocation, real D1 measurement against the defined primary metric.
  3. Measure the D1 outcome. With a real cohort, compute the actual D1 retention rate and compare it against the baseline and target — as real results, not context labels.
  4. Instrument the full funnel in production and measure each stage. The 7-stage funnel exists as a design; the next step is to actually collect the events and report the stages.
  5. Build the cohort dashboard with real cohort progression over time — not the illustrative benchmark model, but real cohort data.
Proposed

None of the above has been done. They are next steps, not evidence.

Key takeaway

Build the measurement system before you claim you've changed the outcome. Define D1, instrument the funnel, compute the calculator, show "not enough data yet" when you don't have it — and be honest that the outcome wasn't measured. The portfolio evidence for Unrot is the measurement thinking, not the retention result.
