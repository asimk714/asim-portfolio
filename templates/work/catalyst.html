Catalyst

A keyboard-first interaction design study — a working product built as vanilla JS with localStorage, demonstrating the interaction paradigm inspired by Linear. Not a clone. Three documented improvements over the reference. No framework. No backend.

Context

Catalyst is a keyboard-first interaction design study — a working product that explores what it feels like to build an interface where the keyboard is the primary input, not the mouse. It was inspired by the interaction paradigm of Linear, the issue tracking tool known for its keyboard-centric UX — but Catalyst is not a clone. It is a demonstration of the paradigm, built from scratch in vanilla JavaScript with localStorage persistence.

The project was built as a single-page application with no framework, no build step, and no backend. Every interaction is handled in the browser, and state persists in localStorage. The goal was to show that the keyboard-first paradigm can be implemented cleanly without a large framework or complex infrastructure.

Problem / Motivation

Proposed

The motivation below is a product decision. It is not validated with users.

Many tools assume the mouse is the primary input and the keyboard is secondary. Catalyst explores the opposite: what if the keyboard were primary, and the mouse were the accommodation? The hypothesis is that a keyboard-first interface can feel fast and focused for certain kinds of work — navigating lists, moving between items, performing actions — without requiring a mouse for every step.

This is an interaction design study, not a market-validated product. There is no evidence that users prefer keyboard-first interfaces for this kind of task, or that Catalyst's specific implementation is better than alternatives. The value is in demonstrating the paradigm, not in proving demand.

Product Decision

Proposed

The decisions below are product choices. They are not validated with users.

Catalyst was built as a vanilla JS application with no framework, no build tool, and no backend. The decision was deliberate: show that the keyboard-first paradigm is achievable without a large technology stack. localStorage handles persistence. The entire application runs in a single HTML file with embedded JavaScript and CSS.

Stack decision

Vanilla JS + localStorage. No framework. No build step. No backend. One HTML file. This keeps the project simple, portable, and focused on the interaction design rather than the infrastructure.

Not a clone

Catalyst was inspired by Linear's keyboard-centric interaction paradigm, but it is not a Linear clone. It demonstrates the paradigm — keyboard navigation, keyboard actions, keyboard-first modal flow — in a simplified issue-tracking interface. The visual design, the feature set, and the interaction details are Catalyst's own.

How It Works

Catalyst presents a list of issues (or tasks) that can be navigated and acted on entirely from the keyboard. The core interaction loop: navigate the list with j/k, open an item with Enter, close modals with Escape, search with /. State persists in localStorage, so the list and any changes survive a page reload.

Key Action
j Move down the list
k Move up the list
Enter Open the selected item
Escape Close the current modal / cancel
/ Focus the search field

The interface is organized around a focused list view with a modal overlay for detail. When an item is selected and opened, a modal appears with the item's details. The modal can be closed with Escape or by clicking outside it. Search filters the list in real time.

Three Documented Improvements

Hypothesis

The three improvements below are product decisions. They are documented as improvements over the reference, but they have not been validated with users or measured against a baseline.

Catalyst documents three improvements over the reference interaction paradigm. These are the product's own contributions — decisions about how the keyboard-first experience should work. They are not comparative claims backed by user testing.

Improvement 1 — Progressive Onboarding

Linear's keyboard-centric approach has a steep learning curve — new users see a powerful system but don't know where to start. Catalyst addresses this with progressive onboarding: the first-run experience starts with essential features visible and reveals keyboard shortcuts and advanced features as the user engages. A sample project is pre-populated so the user can experience the paradigm immediately, with a clear option to clear it and start fresh.

Improvement 2 — Visual Progress Dashboard

Linear shows progress through issue counts and cycle views, but creative teams often benefit from more visual progress indication — especially for non-technical stakeholders. Catalyst adds a dashboard with visual progress bars per project, showing completion percentage and task distribution across statuses. The summary view is compact but information-rich, giving a quick health assessment without requiring the user to count or calculate.

Improvement 3 — Contextual Discoverability

Linear's command palette (Cmd+K) is powerful but requires memorization — not all actions are equally discoverable. Catalyst addresses this with a context-sensitive action bar showing relevant actions for the current context (new task, change status, filter). Combined with keyboard shortcuts that ARE shown in the UI (not hidden), and command palette results that display shortcuts for discoverability. The paradigm is discoverable by scanning, not by memorizing.

Not evidenced

These improvements are documented claims, not validated results. There is no user research, no usability testing, and no measured comparison against the reference. The improvements are the product's own design decisions, stated plainly.

Evidence Limits

What Catalyst demonstrates

  • A working keyboard-first interaction paradigm implemented in vanilla JS
  • Keyboard navigation (j/k), modal flow (Enter/Escape), search (/)
  • localStorage persistence
  • A product built as a deliberate interaction design study
  • Three documented improvements over the reference — stated as product decisions

What Catalyst does not claim

  • User research or usability testing
  • Validated demand
  • Measured improvement over the reference
  • Adoption or usage data
  • Production deployment
  • That keyboard-first is better — only that it is a viable paradigm worth exploring

What I Would Validate Next

Proposed

The validation steps below are proposed. None have been done for Catalyst.

  1. Usability comparison. Test whether keyboard-first navigation is faster or more satisfying than mouse-driven navigation for the same task, with real users.
  2. Task completion. Measure whether users can complete core tasks (find an item, open it, perform an action) without using the mouse.
  3. Preference. Ask users whether they prefer keyboard-first or mouse-driven interfaces for this kind of work — and why.
  4. Comparison to reference. Compare Catalyst's interaction paradigm to the reference it was inspired by, in a structured usability study.
Not evidenced

None of the above has been done. Catalyst is a working prototype and an interaction design study. It is not a validated product.
