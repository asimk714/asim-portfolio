Principal PM Operating System

How I actually run product work.

This is not a job title or a formal methodology I'm selling. It's the operating system I use to take a vague problem and turn it into something built, measured, and verified — across product, engineering, data, and stakeholders. Each stage below is anchored to something I've actually done across the three projects on this portfolio.

01

Discover

Identify meaningful problems. Frame them with user segments and JTBD hypotheses. Label assumptions explicitly — before the first line of code is discussed.

Evidence: Unrot D1 retention problem framing + JTBD hypotheses · ReviewFlow AI product principle · Experiment Tracker experiment→decision gap

02

Decide

Prioritize alternatives with explicit criteria. Make trade-offs with rationale. Choose the smallest capability that addresses the most important gap — and record the "why not" for everything left out.

Evidence: Experiment Tracker 7-candidate prioritization with "why not prioritized" · ReviewFlow guardrail decisions · Unrot measurement model over feature breadth

03

Define

Turn ambiguous problems into defined products with clear boundaries, user needs, and success criteria. Write the product brief before any code.

Evidence: Experiment Tracker PRODUCT_BRIEF · ReviewFlow product decisions + MVP prioritization + architecture doc · Unrot measurement model + D1 retention model

04

Build

Build working products across multiple stacks — or work closely with engineering — with verification in mind from the first implementation. Not a slide. Not a prototype that only works in a deck.

Evidence: ReviewFlow (React + Supabase + TypeScript) · Unrot (Next.js + PostgreSQL + Prisma) · Experiment Tracker (Flask + SQLite + Jinja2, 22 tests)

05

Launch

Make the product available to real people. Beta, rollout, GTM, stakeholder communication. Distribution is a product decision, not an afterthought.

Not evidenced All three products are built and verified in local/demo environments. None has a verified public deployment, measured adoption, or GTM strategy.

06

Measure

Define success metrics. Build measurement systems. Design experiments to test hypotheses. Measure before claiming — otherwise the claim isn't worth trusting.

Evidence: ReviewFlow AI quality measurement (247 checks, output evaluator, 15 cases, intervention record) · Unrot measurement model (metric hierarchy, funnel, instrumentation) · Experiment Tracker proposed usage metric

07

Learn

What happened? What worked? What did not? At what confidence level? Learning is where verification meets honesty — and it's where the discipline shows up.

Evidence: ReviewFlow failure analysis + intervention record (honest, not validated) · Unrot analytics design + honest "not enough data yet" state · Experiment Tracker 17-category verification report · KAIRO Verification Truthfulness Protocol

08

Iterate

Feed what you learned back into the next decision. Change the product. Propose the next experiment. Update the roadmap. The lifecycle doesn't end at launch — it loops.

Evidence: Each case study closes with "What I Would Do Next" — specific proposed next steps, never pretending they've been completed · ReviewFlow: live-validate Phase 11 · Unrot: run the A/B experiment · Experiment Tracker: validate user model with real users

The system behind this — and the honest disclaimer

I use a product-engineering methodology called KAIRO — a structured approach to product work that emphasizes evidence discipline, verification truthfulness, and AI-assisted product development. It's the system that encodes the evidence-label discipline you see across this portfolio.

I also use Hermes Agent as my working environment for structured research, analysis, and documentation. KAIRO and Hermes are operating methodology and tooling — they are not customer-facing products, they have no users or commercial outcomes, and they are not claimed as employment or a shipped product.

What this section is: a description of how I work. What it is not: a claim that I hold a Principal PM title, that KAIRO is a product, or that these stages were validated by a hiring manager or a customer.
