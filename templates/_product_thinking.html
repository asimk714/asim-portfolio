01 Discover

Name the real problem before building anything.

  • Identify meaningful problems and frame them precisely.
  • Label assumptions, inferences, and unknowns explicitly.
  • Lead with the deeper problem, not the surface symptom.

Evidence: Unrot D1 retention problem-framing · JTBD hypotheses with assumptions/unknowns labeled · ReviewFlow AI product principle

Observed
02 Define

Turn ambiguous problems into defined products with clear boundaries.

  • Write the product brief before any code — problem, user, JTBDs, scope.
  • Set MVP boundaries: what's in, what's out, and why.
  • Define success criteria before claiming outcomes.

Evidence: Experiment Tracker PRODUCT_BRIEF · ReviewFlow MVP prioritization · Unrot measurement model

Observed
03 Decide

Prioritize with explicit criteria. Make trade-offs with rationale.

  • Evaluate alternatives against a stated question, not a gut feel.
  • Choose the smallest capability that closes the most important gap.
  • Record the "why not" for every option not chosen.

Evidence: ReviewFlow PRODUCT-DECISIONS (8 decisions) · Experiment Tracker 7-candidate prioritization with "why not prioritized"

Observed
04 Build

Build working products across stacks — with verification in mind.

  • Ship real running products, not design concepts or Figma files.
  • Work across multiple stacks: React/Supabase, Next.js/PostgreSQL, Flask/SQLite.
  • Disclose AI assistance where it happened — don't hide it.

Evidence: ReviewFlow CI · Unrot build/lint/typecheck + 35 tests · Experiment Tracker 22 tests

Observed
05 Measure

Define success metrics and build measurement systems before claiming outcomes.

  • Build checks and evaluators before claiming quality.
  • Design measurement to catch its own artifacts — then correct them.
  • Label proposed metrics separately from measured ones.

Evidence: ReviewFlow ai-quality-report (247 checks, output evaluator, 15 cases) · Unrot experiment-plan (power analysis) · Experiment Tracker proposed usage metric

Observed Proposed
06 Verify & Learn

Verify what you claim. Be honest about what you haven't validated.

  • Run independent verification after implementation — not just "does it run?"
  • Correct measurements when they're wrong; document what wasn't validated.
  • Fold learning into verification — no separate "learn" stage.
